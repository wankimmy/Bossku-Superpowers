# Rigorous code review

Assume the change is wrong until the code, tests and callers show otherwise. Review the change, do not rewrite the system. A review request allows analysis only: do not edit files, post comments or submit a review unless asked, and keep any reproduction in a scratch copy (no installers or machine-wide changes).

1. **State the intended outcome** from the request, the PR description and the linked issue (Linear, GitHub), and what is deliberately deferred. Check that the description matches the diff, and that each requirement in the issue is met by the code, quoting the requirement. If intent is unclear, label your assumption and carry on.
2. **Read the evidence, not just the diff:** the whole PR diff against its base (a re-review reads all of it, not only the new commits), the callers, the tests, the types or schemas, and the config or infra it touches. Know the project's current infra architecture (instances, workers, queues, data stores, environments, deploy path) so you judge the change against how it really runs. Read the versions it runs on from the manifest, lockfile or runtime, check the latest stable live (shared bar section 2), and flag any API the change uses that the installed version does not have.
3. **Check CI and the PR's own proof** on the head you review. Run `gh pr checks <n>` (or read the pipeline) and open each failing log. Any failing or pending check, required or not, means no approval, even when it is a known flake fixed elsewhere. A failing check is Request changes: name the check, its log line and a file:line. Use the code line the log points to. If the log gives none (for example a job timeout or runner cancel), use the workflow file:line that runs the failing step, and trace that step's command to the code it runs before requesting changes. A pending check is not a verdict yet: say "approve once <check> is green". Open every screenshot or recording in the PR: it shows this change and matches the code, covers the states and screen sizes the repo asks for, and its before and after are like for like. A UI change with no proof is a finding.
4. **Go through every category; none is skipped.** If one needs something you do not have (a production data copy, access, the linked issue, screenshots), ask the user to prepare it; until it arrives, the verdict is "Provisional (missing: <input>)" and nothing is approved. A category that cannot apply is marked "not applicable: <reason>", which is not a skip:
   - correctness: edge and boundary values, empty and null, ordering, race conditions (two users or jobs on the same row, double submits, check-then-act, queue retries), idempotency, partial failure, retries; walk each what-if scenario through the code
   - business logic: rules and state changes that clash with existing flows, roles or data (detail: `reference.md`)
   - data: run the change against a masked production data copy (personal data and secrets masked), never production, and match production data types and shapes, such as "0.01" text vs 0.01 number (detail: shared bar section 4)
   - API integration (when the change calls or serves an API): endpoint down or slow, retries, extra, missing or retyped fields, and logging with secrets and personal data masked (full list: shared bar section 5)
   - UI/UX (when the change touches a screen, message or flow): read each screenshot and the template as the user would. A message, warning or label that is wrong for that state, contradicts the result, or leaves the user unsure what happened or what to do next is a finding to fix, not a nit (severity per the UI/UX rule in `reference.md`, step 4). So is a state with no feedback, a disabled control with no reason shown, or wording that differs between two places for the same thing
   - structure: follows best practice and the repo's existing patterns and code structure
   - scope: every file in the diff belongs to the change. Agent working files (superpowers plans, `docs/work-items` notes, handoffs, scratch scripts, logs, local config) are a finding to remove, unless the repo keeps them on purpose; then check they are current and match the code. Lasting knowledge goes where the next coder looks: the PR description and issue, tests, a code comment for a non-obvious why, an ADR, the README or a runbook
   - security: validation at every trust boundary, injection, authorization on every path, secrets, error leaks
   - performance: queries in loops, unbounded growth, blocking calls on hot paths, missing indexes
   - tests: the new behaviour, the failure paths and the bug path are covered, and the tests exercise real behaviour
   - compatibility: existing callers, existing users and day-to-day operations, schema and API changes, deprecations
   - operations: logs and metrics that help, migrations (locks on large tables, backfills), deploy order and zero downtime (old code on the new schema, new code on the old), rollback
   - AI-generated code: APIs or library methods that do not exist, catch-all error handling that swallows failures, placeholder validation, boilerplate that does not match the repo
5. **Check the outcome and who is affected** (a short pass, sized to the risk): does the change provide the mechanism for the result it promises, or only describe it? Who or what has to use it: callers, existing data and roles, an agent that must load a rule or doc? How could it pass every check and still miss its purpose? Green CI shows the behaviour the checks cover, not adoption.
6. **Report only what you can point to.** Every finding has a file:line, the evidence, a severity (P0 blocks, P1 must fix, P2 should fix, P3 nit), how you verified it (ran it, traced it, inferred it) and the smallest fix. Keep confirmed defects and unmet explicit requirements apart from optional improvements. A suspected bug, error or broken path is never dropped for low confidence: run it or trace it until it is confirmed or ruled out. Drop any finding you cannot support after you run or trace it, style or otherwise; do not pad, and do not invent a recommendation quota.
7. **Escalate scope** (a larger refactor) only when a small fix cannot work, and say why.

**Review since a fixed point** (a branch, tag or commit the user names): confirm it resolves (`git rev-parse`) and the diff is not empty before reviewing, then use `git diff <ref>...HEAD` so the comparison is against the merge-base. Report two axes separately and do not merge or rerank them: Standards (the repo's documented rules) and Spec (the originating issue or spec: missing or partial requirements, scope creep, requirements that look done but are wrong, each quoting the spec line). Code can pass one axis and fail the other. If no spec exists, mark the Spec axis "not applicable: no spec".

**Smell baseline** for the Standards axis when the repo documents little: possible Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest. These are judgement calls, never hard violations: label them "possible", let a documented repo standard override them, and skip anything tooling already enforces.

Verdict first: approve, approve with nits (P3 only), request changes (any P1 or P2, or a failing check), block (any P0), or provisional (missing: <input>). Approve only when CI is green and nothing is left to fix; a known bug or a path that does not work is never a nit. Then the outcome and impact in a line, the findings most severe first, any material recommendation (smallest change, how to check it, this PR or a follow-up), the CI state of the reviewed head (green, or which check fails and why), and the checks you ran, with your local runs kept apart from external CI. If the diff is clean, say so briefly and still say what the evidence does not show. The full checklists, confidence scoring and optional tool integrations: `reference.md`. The shared quality bar, with version sources per language and the types the same value can arrive as: `../../references/checklists/engineering-quality-bar.md`.
