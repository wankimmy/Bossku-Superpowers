## Concrete execution phases

1. **Complete baseline verification first** — root owns the running full suite. Audit artifacts are the only files changed by this stocktake.

2. **Review/update existing exact ECC subset** — files: `skills/{accessibility,architecture-decision-records,database-migrations}/SKILL.md`, provenance/docs and focused validation. These three have normalized upstream changes; the other seven exact owners are normalized identical. Preserve any recorded local deviations and verify frontmatter/link examples.

3. **Add self-contained unique domains in cohesive batches** — files: each `skills/<target_id>/SKILL.md` from `add-adapt` rows, plus exact attribution. Start with framework/testing/runtime domains, then network/science/healthcare/manufacturing/logistics domains. Framework/API examples use installed versions; high-stakes examples use authoritative current sources and independent review. No arbitrary numeric cap or exclusion because a field is niche. Each batch is independently schema/link/routing-testable.

4. **Review resource-coupled capabilities separately** — 42 source skills have sidecars. `taste-application` has 80 files, `angular-developer` 35 and `remotion-video-creation` 31. Import all required reviewed resources or write a deliberate portable instruction adaptation that names external prerequisites; never leave a thin body pointing at missing scripts. Do not silently bundle executables, generated outputs, sample media or dependencies.

5. **Enhance existing owners** — 109 rows map to existing workflow/domain owners. Compare full bodies against destination and transplant only missing useful capability. Existing vendored owner cannot be reworded in place: first-party companion or upstream-compatible re-vendor. Examples: prompt caching into cost optimisation, change impact into codebase analysis, agent security hardening into trust-boundary guidance, precise component testing receives a new dedicated owner.

6. **Resolve the 19 explicit deferrals** — these are ECC package-control wrappers, deprecated/experimental/unavailable execution runtimes or excluded wallet execution, not niche-domain exclusions. Useful concepts can enhance native Bossku install/finder/doctor/security controls. A runtime-specific skill requires a supported runtime and reviewed integration; no unsupported slash commands or fictional tool claims.

7. **Integrate routing and audit** — files: `bossku/index.py`, generated `skills/skill-index.json`, focused routing tests, `docs/third-party.md`, attribution and provenance registry. Add concrete English/BM/rojak positives, task/domain negatives, optional-provider guards, explicit requests/negations, cross-domain combinations and alternative exclusions. Avoid broad one-word triggers that hijack unrelated tasks. Profile/install checks must ensure new on-demand skills are discoverable without expanding always-loaded context.

8. **Verify each batch then final delivery** — `python -m bossku skills index --root .`; `python -m bossku validate --root .`; targeted routing/frontmatter/resource/provenance checks; `python -m unittest discover -s tests -v`. State optional runtimes unavailable and any API examples not executed. Keep routing evidence separate from actual live-host skill invocation.

- ECC `benchmark-methodology` is competitor scoring. Use `bosskuai-competitor-scoring`; performance baselines enhance performance profiling.
- Relative-link scan candidates can be placeholders inside code/examples rather than broken package dependencies. Resolve them in context, do not automatically remove examples.
- Source 311-skill count is canonical filesystem inventory, not a README estimate. UTF-8/non-ASCII output needs explicit encoding when using Windows console; inventory files are saved as UTF-8.
